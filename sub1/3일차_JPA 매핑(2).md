1. 일대다(1:N) 단방향 매핑의 구조적 한계

테이블 구조상 외래 키는 항상 N쪽에 존재

하지만 일대다 단방향에서는
1쪽 엔티티가 다른 테이블의 외래 키를 관리

이로 인해 연관관계 변경 시 추가 UPDATE SQL 발생

👉 구조가 비직관적이며 성능상 불리
👉 실무에서는 거의 사용하지 않음



2. 일대다 양방향 매핑은 공식적으로 존재하지 않음

JPA 스펙상 일대다 양방향 매핑은 지원되지 않음

아래 방식은 “양방향처럼 보이게 하는 우회 방법”

@JoinColumn(insertable = false, updatable = false)


읽기 전용 필드로 양방향처럼 사용

권장되지 않는 방식

👉 대신 다대일 양방향 매핑 사용이 정석



3. 일대일(1:1) 관계에서 외래 키 위치 선택

일대일 관계에서는 외래 키를 둘 위치를 선택할 수 있다.

주 테이블에 외래 키

- 객체 지향 설계에 적합

- JPA 매핑 단순

- 주 테이블만 조회해도 관계 존재 여부 확인 가능

👉 JPA에서 선호하는 방식

대상 테이블에 외래 키

- 전통적인 DB 설계 방식

- 일대일 → 일대다 확장 시 테이블 구조 유지 가능

- 지연 로딩의 한계 존재

👉 특수한 경우가 아니면 잘 사용하지 않음




4. 다대다(N:M) 매핑의 실무적 문제점
@ManyToMany


문법상 가능하지만 실무 사용 금지



5. 다대다 한계 해결 방법 (연결 엔티티)
N:M 관계
→ 연결 테이블을 엔티티로 승격
→ 1:N + N:1 구조로 재설계


@ManyToMany 제거

연결 테이블을 독립 엔티티로 관리

실무에서 사용하는 유일한 다대다 해결 방식



6. 상속관계 매핑 개념

관계형 DB에는 상속 개념이 없음

JPA는 슈퍼타입–서브타입 모델로 상속 표현

@Inheritance(strategy = InheritanceType.JOINED)



7. 상속관계 매핑 전략 비교
JOINED 전략

- 테이블 정규화

- FK 무결성 보장

- 조회 시 JOIN 발생

- 가장 권장되는 전략

SINGLE_TABLE 전략

- 하나의 테이블에 모든 엔티티 저장

- 조회 성능 우수

- NULL 컬럼 증가

TABLE_PER_CLASS 전략

- 자식마다 테이블 생성

- UNION 쿼리 필요

- 사용 비권장



8. @MappedSuperclass (공통 매핑 전용)
@MappedSuperclass
public abstract class BaseEntity {
    private LocalDateTime createdDate;
}


공통 속성 상속 목적

테이블 생성 ❌

조회 대상 ❌

상속관계 매핑과는 완전히 다른 개념

👉 생성일, 수정일 등 공통 컬럼 관리용
