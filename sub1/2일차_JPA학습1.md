# JPA 학습1 – 2일차  
## 도메인 분석 기반 엔티티 구성과 연관관계 매핑 원칙

---

## 학습 주제
도메인 분석을 통해 엔티티와 값 타입을 구분하고, 연관관계 매핑의 기준을 정리한다.

---

## 학습 내용

### 1. 도메인 분석을 통한 엔티티/값 타입 구분 기준

쇼핑몰 예제를 기준으로 다음 구성 요소를 학습 대상으로 정리하였다.

- Member (회원)
- Order (주문)
- OrderItem (주문상품)
- Item (상품)
- Delivery (배송)
- Address (주소 – 값 타입)

구분 기준은 다음과 같다.

- 식별자(ID)를 통해 추적·변경 관리가 필요한 경우 → 엔티티
- 단순 값 묶음이며 독립적인 생명주기가 필요하지 않은 경우 → 값 타입

이 기준이 필요한 이유는 엔티티는 동일성(ID)으로 관리되며,  
값 타입은 공유·변경 추적 시 제약이 존재하기 때문이다.

---

### 2. 주문–상품 관계에서 중간 엔티티(OrderItem)의 필요성

주문과 상품은 개념적으로 다대다(N:M) 관계이지만,  
실무 및 ORM 환경에서는 다대다 관계를 직접 사용하지 않는 구조를 학습했다.

중간 엔티티(OrderItem)가 필요한 이유는 다음과 같다.

- 주문과 상품의 관계 자체에 저장해야 할 데이터가 존재
  - 주문 수량(count)
  - 주문 당시 가격(orderPrice)
- 다대다 관계로는 관계 데이터의 확장이 어려움
- 주문 취소, 재고 복구 등의 비즈니스 로직 처리 단위가 모호해짐

정리된 관계 구조는 다음과 같다.

- Order 1 : N OrderItem
- OrderItem N : 1 Item

---

### 3. 연관관계 매핑과 주인 개념(FK 기준)

연관관계의 주인은 외래키(FK)를 실제로 관리하는 쪽으로 정리하였다.

이 기준이 필요한 이유는 DB 변경은 FK 업데이트로 발생하며,  
주인이 아닌 쪽에서 값을 변경해도 DB에 반영되지 않기 때문이다.

관계 정리(쇼핑몰 예제 기준):

- Order → Member  
  - FK: orders.member_id  
  - 주인: Order.member

- OrderItem → Order  
  - FK: order_item.order_id  
  - 주인: OrderItem.order

- OrderItem → Item  
  - FK: order_item.item_id  
  - 주인: OrderItem.item

- Order ↔ Delivery (1:1)  
  - FK를 가진 테이블 기준으로 주인 설정

반대 방향 연관관계는 조회 편의를 위해 `mappedBy`로만 사용한다.

---

### 4. Address를 값 타입으로 분리하는 이유

Address는 city, street, zipcode의 값 묶음이며  
독립적인 식별자와 생명주기가 필요하지 않다.

값 타입으로 분리하는 이유는 다음과 같다.

- 주소 단독 조회/추적 요구가 없음
- Member, Delivery에 포함되는 개념
- 엔티티로 분리 시 불필요한 테이블과 조인 증가

---

## 정리

- 엔티티와 값 타입은 ID 필요 여부로 구분
- 다대다 관계는 중간 엔티티로 해소
- 연관관계 주인은 FK 기준으로 판단
- 주소는 값 타입으로 포함하여 중복 제거
