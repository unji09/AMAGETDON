# Git FLOW 전략 학습 – 4일차
## Git Branch 전략과 대표 Workflow 비교 정리

## 학습 주제
Git Branch 전략의 목적을 정리하고, 대표 전략(Git Flow / GitHub Flow / GitLab Flow / Trunk-based Development)의 브랜치 구성과 장단점을 비교한다.

## 학습 내용

### 1. Git Branch 전략의 목적

Git Branch 전략은 브랜치 사용 규칙과 협업 workflow를 정하는 것이다.

전략을 두는 이유는 다음과 같다.

- 기능 단위로 브랜치를 분리하여 작업을 병렬로 진행할 수 있다.
- 변경 이력 추적과 문제 발생 시 롤백이 용이하다.
- 개발 브랜치와 배포 브랜치를 분리해 버전 단위 관리가 가능하여 배포 안정성을 높일 수 있다.

전략 없이 브랜치를 사용하면 브랜치 용도 구분, 삭제 여부 판단, 수정/롤백 절차가 복잡해질 수 있다.

---

### 2. 대표 브랜치 전략 종류와 브랜치 역할

#### 2.1 Git Flow (릴리스 중심)

브랜치 종류: `main(master)`, `develop`, `feature`, `release`, `hotfix`

- `main(master)`  
  제품 출시 버전(배포용)을 관리하는 중심 브랜치
- `develop`  
  다음 출시 버전을 개발하는 중심 브랜치
- `feature`  
  기능 개발용 브랜치(개발 완료 후 `develop`에 병합)
- `release`  
  배포 준비 및 QA/버그 수정 브랜치 (`develop`에서 분기)
- `hotfix`  
  운영(`main`)에서 발생한 긴급 버그 수정 브랜치 (수정 후 `main`, `develop`에 반영)

구성 관점:
- `main`, `develop`은 중심 브랜치
- `feature`, `release`, `hotfix`는 필요 시 생성·삭제되는 서포팅 브랜치

운영 시 주의:
- feature 개발 기간이 길어지면 develop 변경분과 충돌 가능성이 커지므로, 작업 중 develop 변경 사항을 주기적으로 반영(리베이스/머지)하여 최신화가 필요하다.

---

#### 2.2 GitHub Flow (단순 + 빠른 배포)

브랜치 종류: `main` + `topic(feature)`

- `main`  
  항상 안정 상태(stable)를 유지해야 하며, 커밋은 빌드/테스트를 통과해야 한다.
- `topic`(또는 feature 브랜치)  
  기능/이슈 단위로 분기하여 작업하고 PR 기반 코드 리뷰 후 `main`에 병합한다.

운영 특징:
- `main`에 머지가 일어나면 자동 배포되도록 설정하는 방식이 자주 사용된다.
- 브랜치 수가 적어 규칙이 단순하며, PR 중심 협업에 적합하다.

---

#### 2.3 GitLab Flow (Git Flow와 GitHub Flow 절충)

브랜치 구성은 서비스 배포 단계(운영/스테이징 등)에 따라 변형된다.

예시 구성:
- `main(master)`  
  Git Flow의 `develop`과 유사한 역할로 운영되는 경우가 있다.
- `feature`  
  기능 단위 개발 브랜치
- `pre-production`  
  배포 전 테스트/검증 브랜치(지속적으로 유지)
- `production`  
  운영 배포 브랜치(배포용)

정리 포인트:
- Git Flow의 `release`와 유사한 역할을 `pre-production`이 담당할 수 있으나,
  `pre-production`은 지속적 배포를 위해 보통 삭제하지 않고 유지된다.
- GitLab은 내장 CI/CD를 통해 빌드/테스트/배포 자동화와 결합하기 쉬운 구조를 제공한다.

---

#### 2.4 Trunk-based Development (TBD)

브랜치 종류: `trunk(main)` 중심

- `trunk(main)`  
  모든 변경사항이 빠르게 통합되는 단일 중심 브랜치
- (선택) 짧은 수명의 feature 브랜치  
  필요 시 만들되, 장기간 유지하지 않고 빠르게 trunk에 병합한다.

적용 성향:
- 작은 규모 또는 릴리스 주기가 짧은 프로젝트에서 단순한 운영이 가능하다.

---

### 3. 전략별 장단점 비교

| 전략 | 특징 | 장점 | 단점 |
| --- | --- | --- | --- |
| Git Flow | 복잡한 브랜치 구조(릴리스 중심) | 버전 관리가 명확, main 안정성 유지 | 규칙 복잡, 브랜치 동기화 작업 증가 |
| GitHub Flow | main + topic 중심(PR 기반) | 단순, 빠른 개발/배포 | 대규모/복잡한 이력 추적 요구에 부적합 |
| GitLab Flow | 절충안(배포 단계 포함) | CI/CD와 결합 용이, 지속적 배포 환경에 적합 | 대규모 팀에서 프로세스 설계가 더 필요할 수 있음 |
| TBD | trunk 중심(빠른 통합) | 통합 빠름, 브랜치 관리 단순 | 실수 전파 위험, 큰 기능/복잡한 프로젝트에서 부담 |

---

### 4. 추가 정리(애매했던 포인트)

- Git Flow에서도 CD 구현은 가능하나, 릴리스 중심 구조이므로 지속적 배포를 하려면 자동화/규칙 보완이 필요하다.
- GitHub Flow의 topic 브랜치는 feature 브랜치보다 일반적으로 생명 주기가 짧고, 빠른 피드백/리뷰 흐름에 초점이 맞춰진다.
- GitLab Flow의 `pre-production`은 Git Flow의 `release`와 유사한 목적을 가지지만, 지속적 배포 환경에서 검증 단계를 위해 유지되는 경우가 많다.
- GitHub Flow는 PR 기반 코드 리뷰 + CI 통과를 강하게 전제하는 운영 방식이다.
- TBD는 단일 브랜치로 빠르게 통합하는 방식이므로, 작은 단위 변경과 자동화 테스트 환경과의 결합이 중요하다.

## 요약 정리

- 브랜치 전략은 협업 규칙과 workflow를 정해 병렬 개발, 이력 추적, 배포 안정성을 확보하기 위한 방식이다.
- Git Flow는 릴리스 중심으로 브랜치 역할이 세분화되어 있으나 운영 규칙이 복잡해질 수 있다.
- GitHub Flow는 main 안정성 + PR 중심으로 단순하고 빠른 배포 흐름에 적합하다.
- GitLab Flow는 배포 단계(스테이징/운영)를 포함한 절충안으로 CI/CD와 결합하기 쉽다.
- TBD는 trunk 중심 빠른 통합을 목표로 하며 작은 변경 단위 운영에 적합하다.
